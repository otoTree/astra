# 5090 单卡单 Worker 规模与成本测算

## 1. 测算口径

本测算只计算 GPU 直接成本和吞吐，不代表最终售价或净利润。假设如下：

| 项目 | 假设 |
| --- | ---: |
| GPU 型号 | NVIDIA RTX 5090 |
| Worker/GPU | 1 个 Worker 使用 1 张 GPU |
| 单 Worker 并发 | 1 个任务（`max_concurrency=1`） |
| 用户视频 | 每个任务固定生成 15 秒视频 |
| 单任务服务时间 | 14 分钟，包含模型加载/预热后的本次完整工作流时间 |
| 并发规模 | 300 个 Worker、300 个同时到达任务 |
| GPU 价格 | 3 元 / GPU·小时 |
| 余量、失败重试、启动费 | 不计 |
| 其他成本 | 存储、流量、控制面、人工、税费暂不计 |

这里的“14 分钟”是 GPU 服务时间，不是视频时长。所有容量和成本按服务时间计算。

本测算按用户给出的 14 分钟作为每个任务占用 Worker 槽位的完整时间。如果其中约 2 分钟只是第一次启动/预热、后续任务不再重复，则稳态应改用实际的 12 分钟服务时间重新测算；本文不擅自扣除这 2 分钟。

## 2. 基线结果

### 2.1 单任务和单 Worker

```text
单任务 GPU 成本 = 3 元/小时 × 14/60 小时
               = 0.70 元/任务

单 Worker 理论吞吐 = 60/14
                   = 4.2857 个任务/小时
```

一个 15 秒视频消耗 0.70 元的 GPU 直接成本，对应每个 GPU·小时产出约 `64.2857` 个视频秒，即 `1.0714` 个视频分钟。

### 2.2 300 个 Worker 的稳定连续吞吐

```text
GPU 数量                 = 300 张
固定 GPU 成本             = 300 × 3 = 900 元/小时
理论吞吐                 = 300 × 60/14
                         = 1,285.714 个任务/小时
                         ≈ 21.4286 个任务/分钟
每小时生成内容           = 1,285.714 × 15 秒
                         = 19,285.714 视频秒
                         ≈ 321.43 视频分钟
                         ≈ 5.357 小时成片
稳定状态单位 GPU 成本    = 900/1,285.714
                         = 0.70 元/任务
```

这是“队列持续有任务、Worker 不空闲”的长期平均值。300 个用户必须持续补充任务，才能达到这个吞吐。

### 2.3 300 个任务同时到达时的首小时波次

如果队列持续有任务补充，所有 Worker 立即开始；每 14 分钟完成一波：

| 时间点 | 已完成任务 | 正在运行 | 说明 |
| ---: | ---: | ---: | --- |
| 14 分钟 | 300 | 0（若没有新任务） | 第一波完成 |
| 28 分钟 | 600 | 0 | 第二波完成 |
| 42 分钟 | 900 | 0 | 第三波完成 |
| 56 分钟 | 1,200 | 0 | 第四波完成 |
| 60 分钟 | 1,200 | 300 | 第五波已启动但尚未完成 |

若只有 300 个任务在 `t=0` 一次性提交，则只会完成第一行的 300 个任务，14 分钟后 Worker 进入空闲或缩容。若队列持续有任务，`t=56` 启动第五波，60 分钟时第五波尚未完成，因此首个自然小时的“已完成数”是 1,200，长期平均吞吐仍是 1,285.714 个/小时。

这一区别很重要：

- **固定租用 300 张卡一小时**：成本固定为 `900 元`。
- **只执行一批 300 个任务并在完成后缩容**：实际 GPU 时间为 `300 × 14/60 = 70 GPU·小时`，成本约 `210 元`，不计启动和预热开销。
- **一批 300 个任务但不缩容，空等满一小时**：成本仍为 `900 元`，按 300 个任务摊销为 `3 元/任务`，这是明显的容量浪费。

如果“300 并发”指 300 个持续活跃用户，则每 14 分钟至少要有新一波任务进入；如果只指一次性 300 个请求，应采用弹性缩容，不能按全年 300 卡常驻估算。

## 3. 收益敏感性

设每个完成视频的实际收入为 `p` 元，不含退款和折扣。

### 3.1 稳定连续运行一小时

公式：

```text
hourly_revenue = 1,285.714 × p
gpu_gross_profit = hourly_revenue - 900
gpu_gross_margin = 1 - 0.70/p
```

| 单视频收入 `p` | 小时收入 | 扣 GPU 后毛利 | GPU 毛利率 |
| ---: | ---: | ---: | ---: |
| 1 元 | 1,285.71 元 | 385.71 元 | 30.0% |
| 2 元 | 2,571.43 元 | 1,671.43 元 | 65.0% |
| 3 元 | 3,857.14 元 | 2,957.14 元 | 76.7% |
| 5 元 | 6,428.57 元 | 5,528.57 元 | 86.0% |
| 10 元 | 12,857.14 元 | 11,957.14 元 | 93.0% |

稳定连续运行的 GPU 直接成本盈亏平衡价为 `0.70 元/视频`。实际对外定价至少还应覆盖存储、流量、失败重试、控制面、运维、税费和利润目标。

### 3.2 首小时完成数口径

按“第 60 分钟已经完成的 1,200 个任务”核算，固定成本仍是 900 元：

```text
首小时 GPU 摊销成本 = 900/1,200 = 0.75 元/已完成任务
首小时收入         = 1,200 × p
首小时 GPU 毛利     = 1,200 × p - 900
```

因此 `0.75 元`是首小时波次口径，`0.70 元`是稳定连续运行口径。不能用首小时 1,200 个完成数否定长期理论吞吐，也不能用长期吞吐掩盖突发开始时的波次边界。

## 4. 推理加速带来的规模收益

保持 300 张 GPU 和 3 元/GPU·小时不变，若通过模型预热、Block Cache、Attention 后端或工作流优化把服务时间从 14 分钟降到下表数值：

| 单任务时间 | 理论任务/小时 | GPU 成本/任务 | 相对 14 分钟吞吐提升 | 固定池小时成本 |
| ---: | ---: | ---: | ---: | ---: |
| 14 分钟 | 1,285.714 | 0.70 元 | 基线 | 900 元 |
| 12 分钟 | 1,500.000 | 0.60 元 | +16.7% | 900 元 |
| 10 分钟 | 1,800.000 | 0.50 元 | +40.0% | 900 元 |
| 8 分钟 | 2,250.000 | 0.40 元 | +75.0% | 900 元 |
| 7 分钟 | 2,571.429 | 0.35 元 | +100.0% | 900 元 |

加速收益不是只体现在单位成本下降，也体现在同一小时可以服务更多用户。例如单视频收费 3 元时：

- 14 分钟：小时 GPU 毛利约 `2,957.14 元`。
- 10 分钟：小时 GPU 毛利约 `4,500 元`，比基线增加 `1,542.86 元/小时`。
- 8 分钟：小时 GPU 毛利约 `5,850 元`，比基线增加 `2,892.86 元/小时`。

这些是数学敏感性，不是质量保证。步数、LoRA、Block Cache、Attention 或分辨率变更必须分别通过质量门，不能按宣传倍速直接写入生产容量。

## 5. 扩缩容和容量策略

### 5.1 无余量的基线

本次假设不配置余量，所以 300 个同时到达任务需要 300 个可调度槽位才能零等待启动：

```text
required_workers = ceil(concurrent_tasks / max_concurrency)
                 = ceil(300 / 1)
                 = 300
```

如果只有 100 张卡，首波只能启动 100 个任务，剩余 200 个排队；每 14 分钟再释放 100 个槽位。若持续有 300 个并发需求，100 卡的理论吞吐只有 `428.571 个/小时`，无法排空到达率。

### 5.2 目标利用率版本

生产通常不能把目标利用率设为 100%。若以 `U=0.8` 作为扩缩容目标，且希望持续承接每 14 分钟一波 300 个任务：

```text
arrival_rate = 300/14 = 21.4286 个/分钟
desired_workers = ceil(arrival_rate × 14 / U)
                = ceil(300/0.8)
                = 375
```

375 张卡的小时 GPU 成本为 `1,125 元`，但它提供约 20% 的突发和建机缓冲；本题的“无余量”基线仍是 300 张卡、900 元/小时。是否购买这 75 张缓冲卡，应由排队 SLO、预算和失败成本决定，而不是硬编码。

### 5.3 规模效益判断

调度器应使用以下决策：

```text
desired_workers = clamp(
  ceil((queued_gpu_seconds + running_remaining_gpu_seconds
        + forecast_arrival_gpu_seconds * planning_window)
       / (service_time_seconds * target_utilization)),
  min_replicas,
  max_replicas
)
```

扩容收益为减少等待带来的业务价值，减去新增 GPU 成本、冷启动成本和失败风险；缩容只能选择空闲或 `draining` Worker，不能终止 14 分钟任务。若一次性 300 个任务在 14 分钟后没有后续流量，弹性策略应立即进入排空和缩容冷却，而不是继续支付 300 张卡的空闲小时。

## 6. 未计入的成本和风险

本测算没有包含：

- 共绩建机、镜像拉取、模型预热和回收时间。
- 任务失败重试、Worker 失联、GPU Xid/OOM 和供应商超时。
- S3/MinIO 存储、输入输出流量和跨区域传输。
- PostgreSQL、Redis、Kafka、控制面和管理台成本。
- 5090 机器的宿主机、机房、电力、带宽、折旧和运维。
- 退款、内容审核、人工质量复核和客户支持。

因此 `0.70 元/视频`只能称为**理论 GPU 直接成本**，不能直接当作最终毛利或对外报价。

## 7. 可执行结论

1. 若 300 个任务持续有新任务补充，300 卡基线每小时完成约 `1,285` 个 15 秒视频，GPU 成本约 `900 元/小时`，长期单位 GPU 成本约 `0.70 元/视频`。
2. 若只有一次性 300 个任务，14 分钟即可完成；应按约 `210 元` GPU 使用成本估算，并在任务完成后缩容。固定运行一小时会把成本抬到 900 元。
3. 价格低于 `0.70 元/视频`时，稳定连续运行无法覆盖 GPU 直接成本；首小时波次口径的临界点是 `0.75 元/视频`。
4. 将服务时间从 14 分钟降到 10 分钟，理论吞吐提升 40%，单位 GPU 成本降到 0.50 元；从 14 分钟降到 8 分钟，吞吐提升 75%，单位 GPU 成本降到 0.40 元。
5. 这些数字应进入调度器的 Release 基准：按真实 P75 GPU 服务时间预测排队、扩容和成本，不能用“15 秒视频时长”作为容量参数。
